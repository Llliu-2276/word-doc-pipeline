# 文档工程与目录约定

适用范围：本文件规定以 Markdown 为唯一源文件、经脚本生成 docx、再由 Word 手工导出 PDF 的文档工程应如何组织目录、命名文件、维护台账与传播变更，供在本 Skill 落地的任意软件工程文档项目使用；文中 ChronoMed-Safe 的具体取值标注为「示例/默认值」。

## 一、核心原则

| 编号 | 原则 | 具体含义 |
| --- | --- | --- |
| P1 | md 是唯一真源 | 正文、表格、图注、表注只写在 .md；docx 与 PDF 均为派生物 |
| P2 | 成品不手改正文 | .docx 只允许手工补封面、插入目录、更新域；正文改动必须回到 .md 再重新生成 |
| P3 | 一文档一目录 | `docs/<文档类型>/` 存放该类文档的 md、docx、PDF、配图、附件 |
| P4 | 过程可复现 | 每份成品都能由「源文件 + 脚本命令 + 固定手工步骤」重新产出 |
| P5 | 台账同步 | 文档进度表、图表绘制说明、一致性核查报告必须与磁盘实际文件一致 |

| 文件 | 角色 | 产生方式 | 可否手改 |
| --- | --- | --- | --- |
| `<文档名>.md` | 唯一真源 | 人工写作 | 只能改这里 |
| `<文档名>.docx` | 派生成品 | `python scripts/md2docx.py <输入.md> <输出.docx>` | 仅封面与目录 |
| `<文档名>.pdf` | 提交成品 | Word「另存为 PDF」 | 否，重新导出 |
| `images/figX-Y.png` | 图件成品 | Visio 导出 | 否，改 .vsdx 后重导 |
| `images/figX-Y.vsdx` | 图件源文件 | Visio 手绘 | 是 |
| `图表绘制说明.md` | 图件台账 | 人工维护 | 是 |

## 二、推荐目录结构

```text
<项目根>/
├─ docs/
│  ├─ 封面.docx                     # 封面底版，Word 手工排版参考
│  ├─ 文档一致性核查报告.md          # 跨文档冲突与缺口清单
│  ├─ 文档格式规范/                 # 格式规范本体（md + docx）
│  ├─ <文档类型>/                   # 每类文档一个目录
│  │  ├─ <文档名>.md                # 唯一真源
│  │  ├─ <文档名>.docx              # 脚本生成
│  │  ├─ <文档名>.pdf               # Word 导出
│  │  ├─ 图表绘制说明.md            # 有配图时必备
│  │  ├─ images/                    # 配图，png 与 vsdx 同名
│  │  ├─ 附件/                      # 外部参考资料（只读）
│  │  ├─ 资料/                      # 调研底稿、过程材料
│  │  ├─ 证据截图/                  # 证据类截图，按组分子目录
│  │  └─ .gitkeep                   # 占位，保证空目录入库
│  └─ ...
├─ scripts/
│  └─ md2docx.py                    # 转换脚本
├─ .gitignore
└─ CLAUDE.md / README.md            # 项目约定与文档进度表
```

- `assets/`、`references/`、`scripts/` 属于 Skill 自身，与被规范的项目目录分离；项目侧只关心 `docs/` 与转换脚本。
- 空目录用 `.gitkeep` 占位（如 `docs/UML设计文档/.gitkeep`），保证目录结构随仓库交付。

## 三、文档类型清单

| 目录名 | 文档 | 编号/依据 | 是否含图 |
| --- | --- | --- | --- |
| 选题报告 | 选题报告 | 课程/立项要求 | 可选 |
| 可行性分析报告 | 可行性分析报告 | GB/T 8567 可行性分析 | 可选 |
| 功能分析说明书 | 功能分析说明书 | GB/T 8567 需求规格说明 | 是 |
| 数据库设计说明书 | 数据库设计说明书 | GB/T 8567 数据库设计说明 | 是 |
| UML设计文档 | UML 设计文档 | 课程要求 | 是 |
| 界面设计文档 | 界面设计文档 | 课程要求 | 是 |
| 项目代码规范 | 项目代码规范 | 团队约定 | 否 |
| 测试文档 | 测试文档 | 测试计划/用例/报告 | 可选 |
| 文档格式规范 | Word 文档格式规范 | 本项目规范 | 否 |
| 竞品分析报告 | 竞品分析报告 | 课程附加要求 | 是 |

新增文档类型的四步：新建同名目录并放 `.gitkeep`；按「文档名 = 目录名」命名 md；在项目进度表中加行；判定其图、表、参考文献是否受本 Skill 约束（默认受约束）。

## 四、文件成对与命名规则

- 三件套同名：`功能分析说明书.md`、`功能分析说明书.docx`、`功能分析说明书.pdf` 必须完全同名、同目录。
- 文档名与目录名一致；使用中文名，不用空格；需要限定版式时用全角括号，如 `数据库设计说明书（3.3.2小节节选）.md`。
- 文件名不带日期、不带 v1/v2 版本号；版本由 git 提交与封面日期体现。
- 编码统一 UTF-8（无 BOM）；换行统一 LF 或 CRLF 均可，但同一仓库保持一致。
- 图片文件用图表编号命名：`fig4-1.png` 为正文引用件，`fig4-1 系统总体 ER 图.png` 为带图名副本，`.vsdx` 与 PNG 同名同目录。

## 五、提交版与节选版

| 场景 | 命名方式 | 处理规则 |
| --- | --- | --- |
| 完整版 | `<文档名>.md/.docx/.pdf` | 默认交付件 |
| 只需提交某小节 | `<文档名>（<章节号>小节节选）.md/.docx/.pdf` | 另存独立 md，不覆盖完整版 |
| 节选版图表 | 图/表按节选版章节重新编号（如 fig3-1、表 3-1） | 图片可复制改名，图注同步改号 |
| 节选版目录 | 单独在 Word 中插入并更新域 | 不沿用完整版目录 |

- 节选版与完整版各自独立维护；正文口径以完整版为准，节选版只做裁剪与重编号。
- 历史文档中曾把节选版称为「提交版」；现行磁盘文件（`数据库设计说明书（3.3.2小节节选）`）以「小节节选」为准，引用时以实际文件名核对。

## 六、配图、附件、资料与证据截图

| 目录 | 内容 | 是否入库 | 命名 |
| --- | --- | --- | --- |
| `images/` | 正文配图、Visio 源文件 | 是 | `figX-Y.png`、`figX-Y.vsdx` |
| `附件/` | 外部参考资料 PDF、模板、要求文件 | 是（体积大时可评估） | 保留原文件名 |
| `资料/` | 调研底稿、访谈记录、数据表 | 是 | `00-`、`01-` 顺序编号，配 `README.md` 说明 |
| `证据截图/` | 佐证截图 | 是 | `E-<组字母>-<序号>[-子字母]-<名称>.png` |

- 图件的绘制方式、导出规格（PNG 宽度等）、图注写法与引用规则见 [04-图表与表格规范.md](04-图表与表格规范.md)；本文件只规定图件存放位置与入库要求。
- 每套配图必须配 `图表绘制说明.md`，作为图件台账，至少含：图清单与进度表、符号与布局约定、文件命名与导出规格、审查与插入流程。
- 证据截图按对象分子目录（`竞品A-药管家/`），序号连续、名称写清界面用途，同一界面多张用 `a/b/c` 后缀。
- md 只引用 `images/` 下的 PNG；`.vsdx` 不进入正文，仅供修改与审查。

## 七、变更传播链

| 触发改动 | 必须完成的后续动作 | 验证方法 |
| --- | --- | --- |
| 改 md 正文/表格/图注 | 重新生成 docx → 补封面 → 插入并更新目录 → 导出 PDF | 抽查字体、图表、页数、目录页码 |
| 改图（.vsdx） | 重新导出同名 PNG → 更新绘制说明状态 → 确认 md 引用未变 | 图片数统计与 md 引用数一致 |
| 新增/删除图或表 | 重排编号（按章连续）→ 改正文引用 → 更新绘制说明图清单 | 全文搜索「图 x-」「表 x-」无断号、无悬空引用 |
| 改 Word 格式规范 | 核查存量 docx 是否仍符合 → 重新生成受影响文档 | 按验收清单逐项抽查 |
| 改需求/数据口径 | 写跨文档一致性核查报告 → 形成决策记录 → 按决策同步各文档 | 决策表「落实状态」列全部有结论 |
| 改文件名或目录名 | 改 md 内引用、进度表、git 历史说明 | 全仓库搜索旧名，零命中 |

- 传播顺序固定为「源文件 → 派生文件」，禁止反向：不得先在 docx 里改内容再回填 md。
- 一批改动完成后一次性重出 docx 与 PDF，避免多次生成造成成品与源文件脱节。

## 八、交付流程

| 阶段 | 动作 | 完成标志 |
| --- | --- | --- |
| 定稿 | 关闭待决问题，一致性核查无 H 级未决项 | 进度表标「正文完成」 |
| 出成品 | 重生成 docx → 补封面 → 插入并更新目录 → 导出 PDF | 三件套同日更新 |
| 自检 | 按 [06-验收检查清单.md](06-验收检查清单.md) 抽查页面、字体、图表、页数 | 检查项逐条勾选 |
| 命名核对 | 三件套同名同目录；节选版带括号标识；图表编号连续 | 目录树与命名规则一致 |
| 提交 | 提交 md、docx、PDF、配图、绘制说明与规范文件 | git 提交说明写明重出范围 |
| 归档 | 更新进度表与一致性核查报告 | 台账与磁盘一致 |

- 提交前必须确认 PDF 由最新 docx 导出：docx 时间戳应不晚于 PDF，且 PDF 首页为封面、目录页码与正文一致。
- 交付物清单按文档类型裁剪：含图文档必须带 `images/` 与 `图表绘制说明.md`；规范类文档可只交 md + docx。
- 对外提交（课程平台、评审）前清理临时文件与锁文件，避免把 `~$`、`.vsdx` 中间态一并提交。

## 九、进度表维护

- 位置：项目 `CLAUDE.md` 或 `README.md` 的「文档与配图进度」表；Skill 自身不保存具体项目进度。
- 建议列：文档 / md / docx / PDF / 进度说明；状态词限定为「未开始 → 正文完成 → 已生成 → 已定稿」。
- 每次生成 docx、导出 PDF、补完封面目录后立即更新对应单元格，并写日期。
- 中断恢复依据：进度表 + `图表绘制说明.md` 的状态列 + 一致性核查报告的未落实项；三者一致才能判断可继续。
- 至少在每个里程碑（文档定稿、提交前）核对一次台账与磁盘实际文件。

## 十、跨文档一致性核查

- 单文件承载：`docs/文档一致性核查报告.md`，不拆成多份。
- 五步做法：定范围（列出待核查文档与成品）→ 采事实（章节、模块数、表数、图数、口径）→ 交叉比对 → 分级列问题（位置、现象、影响、建议、处理顺序）→ 形成决策记录（编码 H/M/L + A/B 后缀，A=采纳、B=维持现状）。
- 决策记录须含「落实状态」列：已改哪些文件、哪些仅记录不回改。
- 使用约定：改正文前先查报告；未落实的问题不得当作已定稿；报告本身也要随决策更新。
- 优先级口径：H=影响需求/数据基线，M=影响表述一致或可追溯性，L=措辞与编号。

## 十一、git 忽略与提交物

| 忽略项 | 原因 |
| --- | --- |
| `~$*.docx`、`~$*.vsdx`、`~$$*.vsdx` | Office/Visio 打开时的锁文件与临时文件 |
| `.claude/`、`.dsh-acl-recovery/` | 本地 AI/Agent 工具产物 |
| `*.class`、`*.log`、`hs_err_pid*`、`replay_pid*` | Java 构建与崩溃日志 |
| `*.zip`、`*.rar`、`*.jar` 等打包件 | 二进制大文件，按需单独管理 |

- 必须入库：md、docx、PDF、PNG、VSDX、图表绘制说明、`.gitkeep`、转换脚本、规范文件。
- `*.zip` 类规则可能误伤随仓库保存的打包资料；确需入库时用 `git add -f` 或调整规则。
- docx/PDF 为二进制，重新生成会产生整文件 diff；建议一次改动完成后连同 md 一起提交，提交说明写清「重出 docx/PDF」。

## 十二、从零启动新项目的步骤

1. 建 `docs/` 与各文档类型目录，空目录放 `.gitkeep`。
2. 放入 `scripts/md2docx.py`，安装 python-docx，用一份小样例验证转换可跑通。
3. 建 `docs/文档格式规范/Word文档格式规范.md`，内容取自本 Skill 的 `02-Word格式规范.md` 并按项目调整页面参数。
4. 建 `docs/封面.docx` 空白底版，确定校名、信息表、日期等封面要素。
5. 配置 `.gitignore`，先加入 Office/Visio 临时文件与工具产物条目。
6. 在 `CLAUDE.md`/`README.md` 写明文档约定、转换命令、进度表初始行。
7. 选一份文档做试点：写 md → 转换 → 补封面目录 → 导出 PDF，跑通全流程。
8. 为该文档建 `images/` 与 `图表绘制说明.md`，确定图件命名与导出规格。
9. 试点通过后批量推进其余文档，按第七节传播链维护。
10. 每个里程碑做一次跨文档一致性核查，问题进入报告与决策记录。
